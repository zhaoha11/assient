# 更换推拉流服务器：SRS 与自研 RTMP Server 延迟 A/B

状态：自研 RTMP Server 的 A 组初测延迟约 55～80 ms；SRS 已启动，首轮接入因发布端 RTMP connect 缺少 `tcUrl` 被拒绝，客户端已按最小方案补齐该字段并完成编译与 AMF 字节级验证（2026-09-30）。SRS 侧的实际互通与后续 A/B 重测仍待完成，在两者完成前不能判断服务端是否是主要瓶颈。

## 目标与边界

只替换 RTMP 中转服务：A 为现有 `ENET/RtmpServer`，B 为 SRS。被控端采集/编码/推流、SigServer 信令、控制端 FFmpeg 拉流/解码/显示，以及两端的运行机器和网络路径保持一致。先验证 SRS 能接收当前自研发布端，并让现有拉流端播放，再比较稳定播放阶段的画面延迟、抖动和重连行为。

现有地址由被控端 `ECloudAssistant/Net/SigConnection.cpp::doCtreatStream()` 生成，为 `rtmp://192.168.3.130:1935/live/<序号>`；SigServer 只转发地址，控制端 `AVPlayer` 将它交给 `AVDEMuxer`。两种服务器依次在同一台 `192.168.3.130` 上监听 `1935`；完成下方 `tcUrl` 兼容修复后，A/B 切换时不再修改客户端或信令。两服务不能同时占用此地址和端口；每次切换前先停止当前服务，并确认新服务已监听。若 SRS 必须部署在另一台主机，主机、网络和 URL 也会随之改变，这组数据只能做连通性验证，不能用于归因服务端延迟。

## 实验前记录

1. 记录客户端和 ENET 代码提交、客户端二进制、SRS 版本与配置文件哈希、宿主机/虚拟机资源、网络连接方式。A/B 全程使用同一个客户端二进制，不能夹带编码器或播放器改动。
2. 核对运行时视频为相同的分辨率、30 FPS、12 Mbps、GOP 30、无 B 帧；采集同一个屏幕区域和动态内容。记录 `[PIPE-STATS]` 的实际捕获/编码 FPS、`dup`、`skip` 与编码耗时，避免把发送端退化归因给服务器。
3. 固定一台被控端、一台控制端、同一个目标设备码、同一路由和服务器宿主机。关闭额外 RTMP 订阅者、转码和录制。A/B 的每次试验只允许一个发布者和一个播放器。
4. 历史阶段二的 9 个样本为 44～67 ms、平均约 59.33 ms，但采集/编码及协议代码后来有变化，不能直接作为本次 A 组；必须重新测量 A、B 两组。

## SRS 接入

使用固定版本的 SRS，在原自研 RTMP Server 所在 Linux 主机上运行该版本自带的 `conf/realtime.conf`，先记录文件内容和哈希，不边测边调参。SRS 官方低延迟示例启用 `tcp_nodelay on`、`min_latency on`、`publish.mr off`，并在 `play` 中设置 `gop_cache off`、`queue_length 10`、`mw_latency 100`。这些是 SRS 自身的实时模式参数，不能声称它们与自研服务器内部缓存逐项等价；本实验比较的是“现有自研服务”与“SRS 实时模式”两个可部署方案。配置和启动方法以实际安装版本自带文件为准，参考 [SRS 6.0 官方实时模式示例](https://ossrs.net/lts/en-us/docs/v6/doc/sample-realtime)。

在 Linux 主机上依次操作：

```sh
# A：运行现有 ENET/RtmpServer；B：先停止 A，再启动固定版本 SRS。
# 在 SRS trunk 目录启动；路径和进程管理方式按实际部署记录。
./objs/srs -c conf/realtime.conf
ss -ltnp '( sport = :1935 )'
```

SRS 默认监听 `1935`；保留现有 `/live/<序号>` 地址。先用项目原有被控端发起一次完整控制会话，核对 `NetStream.Publish.Start`、首帧画面、连续音视频、停止和再次连接。`OpenUrl()` 返回成功只表示连接流程启动，不能代替发布成功。若发布或拉流失败，收集发布端状态码、拉流端 `avformat_open_input`/解码错误与 SRS 日志，先解决互通，再测延迟。不要用 FFmpeg 命令行发布的成功代替项目发布端互通。

## SRS 接入时遇到的 Bug（2026-09-30）

- 现象：点击远程监控后，被控端向 `rtmp://192.168.3.130:1935/live/2`（再次尝试为 `/live/3`）推流，5 秒后报 `RTMP publish timeout`，随后返回 `CREATESTREAM ERROR`。
- 原因已由 SRS 日志确认：`Invalid RTMP connect packet without tcUrl`。修复前 `ECloudAssistant/Pusher/rtmp/RtmpConnection.cpp::Connect()` 的 connect 对象只有 `app = "live"` 和 `type = "nonprivate"`，缺少 `tcUrl`，SRS 在 connect 阶段拒绝连接；因此发布端等不到 `NetStream.Publish.Start`。当时尚未进入正常推流阶段，不能据此分析编码或延迟。
- 最小修复方案（**已实施 2026-09-30**）：在 `Connect()` 的 AMF connect 对象中增加 `tcUrl`，根据推流 URL `rtmp://192.168.3.130:1935/live/2` 填为 `rtmp://192.168.3.130:1935/live`；未增加其他可选字段。

修复内容与验证：

- `Pusher/rtmp/rtmp.h` 增加 `Rtmp::GetTcUrl()`，由已解析出的 `ip_`/`port_`/`app_` 复原 tcUrl，避免在连接层重复解析 URL。
- `Pusher/rtmp/RtmpConnection.h/.cpp` 增加成员 `tc_url_`，在构造函数中从 `Rtmp` 对象取出，并在 `Connect()` 中写入 connect 对象的 `tcUrl` 键。
- kind 不变：connect 对象仍为 `app`/`type`/`tcUrl` 三项；`AmfObjects` 是 `unordered_map`，键在包内的排列顺序不固定，SRS 按键取值，不受影响。
- 字节级验证：独立探针按 `Connect()` 的方式编码 connect 包，再用客户端自己的 `AmfDecoder`（与 `HandleInvoke()` 相同的两步解码）读回，得到 `tcUrl = rtmp://192.168.3.130:1935/live` 且与期望值完全一致；`app` 仍为 `live`、流名为 `2`。探针源码在 `ECloudAssistant/build/.../probe/tcurl_probe.cpp`（build 目录已被 .gitignore 忽略）。
- 客户端 Debug 编译链接通过，无新增警告。自研 RTMP Server 不校验 `tcUrl`，补上该字段对 A 组无影响，因此 A、B 两组仍可用同一版客户端。
- 待办：在 SRS 上实测——确认 SRS 日志不再报缺少 `tcUrl`，被控端收到 `NetStream.Publish.Start`，控制端能拉流并看到画面。客户端变更后，A、B 两组都须使用同一新版二进制重新采样；旧版 A 组数据只作参考。

## A/B 采样与判定

按 A→B→B→A 顺序做四段，每段重新建立一次完整控制会话。每段播放稳定后才取样；在同一屏幕画面中同时拍摄被控端的毫秒级参考计时画面和控制端预览画面，差值为端到端视觉延迟。每段至少取 10 组非连续样本，合计每种服务器至少 20 组。相机同一帧内的两个读数相减，避免依赖两台电脑时钟同步。保留原始照片/视频、每次读数和试验时间；不要只保留均值。

每段记录：服务器及配置哈希、开始时间、推/拉流 URL、首次成功发布、首帧时间、视觉延迟样本、`[PIPE-STATS]`、CPU/网络负载、掉线/花屏/音画异常。至少比较中位数、P90 和样本范围，同时看 A/B 两次同组结果是否接近。启动耗时、首帧耗时和稳定播放延迟分开报告，不能混成一个平均值。

只有在两组互通、输入条件一致、A/B 重复段趋势一致且差值超出组内波动时，才能把延迟变化归因于被替换的服务器方案。如果 SRS 把端到端延迟稳定降低了超过原 A 组延迟的一半，可称现有服务端方案是本链路的主要延迟来源；若仅改善一部分，则只称它有可测贡献。若差异不明显，只能说本配置下“替换为 SRS 未显著降低延迟”，不能据此断定两种服务器都没有缓存。若 SRS 更慢，先检查其实时配置、服务资源和兼容性；不得直接调整客户端来让 B 组变快。
