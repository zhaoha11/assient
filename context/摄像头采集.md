# 摄像头采集：第一阶段任务

状态：第一阶段代码已初步实现，已接入摄像头采集、UI 选择及信令透传。双端播放、连续启停和异常设备退出仍待验收；信令服务器需在 Linux 重编译部署。更新：2026-10-06。

## 1. 目标与范围

新增默认摄像头采集，实现会话启动时选择“屏幕”或“摄像头”，复用现有编码、推流和播放链路：

```text
Camera → FFmpeg dshow → 解码／转 BGRA → CPU VideoFrame
                                              ↓
                              H264Encoder（libx264）→ RTMP → AVPlayer
```

第一版采用 FFmpeg＋dshow，先验证单摄像头闭环。音频沿用现有采集链，不新增摄像头麦克风。视频源切换通过停止旧会话、启动新会话完成；默认仍是屏幕。

暂不包含：画中画、双路 RTMP、摄像头 GPU 直通、曝光／变焦控制、热插拔自动恢复、Media Foundation 重构。WGC/GDI 的采集机制、NVENC 参数、H.264 打包和 RTMP 时间戳逻辑保持现状。

## 2. 最小接口调整

推荐只抽出已有的公共取帧与生命周期契约，不把 CameraCapture 继承到 ScreenCapture，也不建设通用插件框架：

```text
VideoSource
├─ ScreenCapture
│  ├─ GDIScreenCapture
│  └─ WGCScreenCapture
└─ CameraCapture
```

`VideoSource` 只负责：`WaitLatestFrame`、`RequestStop`、`Close`、宽高及源帧／发布帧计数，提供虚析构。屏幕索引初始化、GPU 输出配置和共享 D3D11 设备仍放在 ScreenCapture；摄像头自行完成设备初始化。

`RtmpPushManager` 增加 `VideoSourceKind { Screen, Camera }`，只在建立会话时选择、初始化具体来源，之后通过 `VideoSource` 持有与消费。Camera 路径明确使用 CPU BGRA＋软件编码；Screen 路径保留当前 WGC/GDI 选择和退化流程。摄像头打开失败明确返回失败，避免悄悄改成屏幕推流。

编码线程保持统一入口，不增加摄像头专用分支：

```cpp
VideoFrame frame;
while (source->WaitLatestFrame(frame)) {
    encoder->EncodeFrame(frame, frame.sequence - firstSequence, out, &timing);
}
```

以上是调用关系示意，首帧原点及停止检查沿用现有实现。目前 UI 下拉已增加摄像头，信令 `captureBackend` 扩展为 0=GDI、1=WGC、2=摄像头；远端选择须部署新版信令服务器后单独验收。

## 3. CameraCapture 的实现要求

- 检查所用 FFmpeg 构建含 dshow；枚举设备后取首个视频设备作为项目的“默认摄像头”，不硬编码本机设备名称。无设备、被占用或权限不足时输出明确错误并回收已建资源。
- 第一版采用设备默认模式，读取并打印实际宽高、输入格式及声明帧率；不强制所有摄像头支持 1080p60。dshow 使用 `video=<设备名称>` 打开，设备枚举及支持模式可用 `list_devices`／`list_options` 核对。[FFmpeg dshow 官方文档](https://ffmpeg.org/ffmpeg-devices.html#dshow)
- 连续读取、解码，在采集模块内把 NV12、YUY2 或 MJPEG 解码结果统一转换成 BGRA。按实际行跨度处理，发布合法的 `VideoFrame::cpu.data/stride/owner` 和实际尺寸。
- 使用一个有界的最新帧槽位，采集线程发布、编码线程等待；慢消费者取最新帧，不建立无限队列。已交给消费者的缓冲在本次使用结束前不得覆盖或释放。
- 分开记录成功采集的真实帧数和发布数，每秒输出实际采集帧率；声明帧率仅作设备信息，不当作实测速率。
- `RequestStop()` 必须唤醒取帧等待，并使阻塞的设备读取能退出；需针对实际 dshow 后端验证，不能假设设置一个停止标志就能解除 `av_read_frame` 阻塞。停止时先让读取／消费线程退出并 join，再释放 FFmpeg 上下文和帧缓冲；失败回滚和重复关闭应安全。
- 若运行中实际尺寸变化，第一版报错并停止当前会话，重新启动后按新尺寸打开编码器；不把新尺寸直接塞进旧会话。自动无缝重配留待后续。

当前 `CpuFrameView` 只有单个数据指针和 stride，没有多平面 CPU 格式描述；`VideoPixelFormat::Nv12` 的存在不代表 CPU NV12 已能直接接入。第一版统一 BGRA，避免提前扩展帧格式与硬编路径。

## 4. 时间轴与日志

- 使用 `steady_clock` 建立会话起点；`capturedAt` 在实际取得解码帧时采样，包含设备／驱动内部延迟，不宣称是传感器曝光时刻。
- 复用 `AV_Common.h` 的 `MakeSequence`，遇到相同时间格时强制严格递增；新会话重新计数。
- 当前编码时间基为 `1/kTargetFramerate`，目标值为 60；Camera 也使用这套时间格。30fps 摄像头正常情况下序号间隔约为 2，不能每帧简单 `++sequence`，否则媒体时间轴只走真实时间的一半。
- 编码 PTS 继续使用 `sequence - firstSequence`；不为摄像头修改 RTMP 时间戳算法，也不为凑 60fps 人工补帧。

最小日志：设备名称／打开结果、输入格式、实际尺寸、声明帧率、每秒采集帧率，以及 `[PUSH] active video source = Camera`。

## 5. 实施顺序与验收

| 步骤 | 工作 | 验证标准 |
| --- | --- | --- |
| 1 | 最小 VideoSource 接口、CameraCapture、qmake 登记 | MSVC 构建通过；GDI/WGC 取帧与编码回归通过 |
| 2 | 默认摄像头 → BGRA VideoFrame → libx264 | 持续取帧并成功编码／本地解码；宽高、stride、所有权和序号合法 |
| 3 | 接入现有 RTMP 推流和 AVPlayer | 双端实机持续显示摄像头画面；停止再启动正常；回到屏幕模式仍可播放 |
| 4 | 生命周期及失败处理 | 连续启停 20 次，无崩溃、关闭卡死或摄像头占用残留；无设备、被占用、初始化失败和尺寸变化有明确结果 |

只有步骤 3 的双端结果才能证明完整复用成功。编译通过、本地编码成功不能替代 RTMP／播放器验收；未具备的设备或环境条件应明确记为未验证。
