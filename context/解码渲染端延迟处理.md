# 第二阶段：解码渲染端延迟处理

状态：任务2统计与任务三最新帧显示策略已接入，编译链接通过；仍需采集同条件 `[PULL-STATS]` 和端到端延迟数据，验证长期运行、停止及重连。第一阶段 SRS 接入已完成。

## 目的

在推流、服务端和测试条件固定的前提下，量化控制端从 `av_read_frame()` 到画面显示的排队与处理时间，找出持续增加端到端延迟的环节。目标是让远程画面尽量接近最新状态，同时保持正常解码、显示和重连。

当前视频路径：`SRS → AVDEMuxer::FetchStream()/av_read_frame() → H264_Decoder` 的压缩包队列 `→ 解码/转换 → AVContext::video_queue_` 单槽帧队列 `→ AVPlayer::videoPlay()/VideoFramePresenter → Qt::QueuedConnection → OpenGLRender::OnRepaintRequested() → paintGL()`。

## 任务

1. **建立基线。** 使用已能正常推拉的同一套 SRS、客户端、分辨率、帧率和测试画面，记录稳定播放时的端到端视觉延迟、实际播放帧率及异常。保留原始测量样本。
2. **只加统计，不先改播放逻辑。** 每秒汇总：`av_read_frame()` 视频包数、H.264 输入包队列当前/最大长度、每秒解码输出帧数、`video_queue_` 当前/最大长度、`videoPlay()` 取帧/发信号帧数、`Repaint()` 和 `paintGL()` 次数；记录发出 `sig_repaint` 到执行 `Repaint()` 的等待时间，并观察 `Repaint()` 到 `paintGL()` 是否滞后。跨线程队列长度读取必须安全，统计日志本身不能逐帧刷屏。
3. **定位解码后到最终渲染的积压。** 先用 `[PULL-STATS]` 区分 `video_queue_`、Qt 信号队列和 `paintGL()` 的持续滞后；`video_queue_` 偶尔超过 1 不是结论。确认显示侧积压后，按下方任务三方案处理，使远程画面尽量接近最新状态。
4. **只处理已确认的瓶颈。** 若解码后或渲染事件持续积压，评估只显示最新的已解码帧，并统计丢弃帧数。不要直接丢弃任意 H.264 压缩包，以免破坏帧间解码依赖；同时检查音画同步影响。
5. **验证效果。** 在相同条件下对比修改前后的队列峰值、渲染帧率、端到端延迟中位数/P90 和异常；完成停止、再次连接测试。没有可重复的延迟改善或出现明显花屏、卡顿时回退该优化。

完成标准：能用日志指出主要积压位置；若实施优化，能用同条件数据证明延迟改善，且播放与重连正常。

## 任务2落地记录（2026-09-30，精简前）

当时统计点与上文要求一一对应，日志前缀 `[PULL-STATS]`，videoPlay 线程每满一秒汇总输出一行，不逐帧刷屏：

- `av_read_frame()` 视频包数、压缩包队列峰值：`AVDEMuxer::FetchStream()` 在 `put_packet()` 后记录（入队后即峰值时刻）。
- 压缩包队列当前长度：当时由 videoPlay 线程经 `AVDEMuxer::VideoPacketQueueSize()` 加锁抽样；2026-10-04 精简日志后，该查询不再使用，已移除。
- 解码输出帧数、`video_queue_` 峰值：`H264_Decoder::run()` 推帧入队后记录。
- `video_queue_` 当前长度：videoPlay 线程输出时经 `size()` 抽样。
- `videoPlay()` 取帧/发信号帧数：pop 后记录，与发信号一一对应。
- `Repaint()`/`paintGL()` 次数：各自入口记录。
- `sig_repaint` 等待：发送时刻随帧走信号参数（`sig_repaint(frame, emitUs)`），`Repaint()` 入口求差；不用共享时间戳，否则事件队列积压时测不出滞后。
- `Repaint()` 到 `paintGL()` 滞后：`update()` 后挂起本帧进入 `Repaint()` 的时刻，`paintGL()` 入口求差；多次 `update()` 被 Qt 合并时按最后一次计。

跨线程安全：`AVQueue` 的 `empty()/size()` 改为与 push/pop 同锁读取；统计计数器全部为原子量，汇总只在 videoPlay 线程输出。开关 `VideoPullStats::kEnabled`，阶段五验收后整体删除。`AVPlayer::HandleStartStream()` 每次 new pull 会话先 `Reset()`。LocalPlayer 不走这条链路，本地预览不污染计数。

## 2026-10-04 统计日志精简

当时先将每秒一条 `[PULL-STATS]` 精简为 5 个字段：解码率、`video_queue_` 帧队列峰值、`paintGL()` 调用率、Qt 信号等待峰值、通知到绘制滞后峰值。任务三接入后，当前默认输出改为 8 项：解码率、帧队列峰值、队列丢帧、`latest` 覆盖、通知率、实际绘制率、信号等待峰值和绘制滞后峰值。`latest` 覆盖只计 GUI 尚未取走就被替换的帧。读帧调用耗时和视频包间隔仍在内部采集，但不出现在默认日志中，不能仅凭这 8 项归因服务端。

## 任务三：解码后到最终渲染的积压处理方案

**目标与启用条件：** 用连续的 `[PULL-STATS]` 判断积压在 `video_queue_`、Qt 信号队列还是 `paintGL()`；保留修改前的端到端延迟和帧率基线。只有确认解码后到显示侧持续积压，才启用下面的显示策略。偶发的帧队列长度大于 1 不足以判定瓶颈。

**处理路径（latest-frame + single pending render notification）：**

1. H.264 压缩包继续按原顺序送入解码器，不丢压缩包；解码完成后，视频专用的 `video_queue_` 最多保留一帧。新帧到来时替换尚未取走的旧 `AVFrame` 并计入丢弃数；音频队列不改。
2. `videoPlay()` 取帧后，在同一把锁下更新 `latestFrame_`、递增 `producedSeq`，必要时覆盖尚未显示的旧帧。只有 `repaintPending_` 为 false 时，才将其设为 true 并投递一个不携带帧的 Qt 刷新通知；不再为每帧排队一个携带 `AVFramePtr` 的 `sig_repaint` 事件。
3. GUI 通知执行时，在同一把锁下清除 `repaintPending_`，然后调用 `update()`；一个通知只安排一次绘制，不在 GUI 线程用 `do-while` 追赶生产者。`paintGL()` 才从 `latestFrame_` 取得帧、序号和会话号的快照、上传纹理并绘制，成功绘制后按会话号更新已绘制序号。已被 GUI 取走的帧即使尚在绘制，也不计为 `latest` 覆盖。`update()` 只是异步安排绘制，不能在通知执行时就把该帧记为已画完。

**同步与调度不变量：** `latestFrame_`、帧序号、`repaintPending_` 的读写和“是否投递通知”的决定受同一把锁保护，实际投递在锁外进行。清除待处理标记前到达的新帧会被随后执行的 `paintGL()` 读取；清除后到达的新帧可以投递下一通知，避免 lost wakeup。任何时刻最多有一个尚未执行的帧刷新通知，Qt 的 `update()` 可以合并绘制请求。每次 GUI 回调只处理一个通知并返回事件循环；若持续高帧率仍占用过多 GUI 时间，再按屏幕刷新节奏限制通知频率，限速后仍须确保最后一帧能被安排绘制。

**会话生命周期：** 停止、切流和重连时清理旧帧与待处理状态，并给通知与绘制快照附带会话代号；旧会话绘制完成后不得推进新会话序号。GUI 下一次绘制时清除旧纹理，停止与重连会排队触发该次绘制。`AVPlayer::HandleStartStream()` 已重建释放过的 `avDEMuxer_` 并复位 `stop_`；GUI 控件与 GL 纹理操作只在 GUI 线程执行。

**统计与验收：** 当前日志记录视频帧队列替换数、GUI 尚未取走的 `latestFrame_` 覆盖数、实际绘制帧率和绘制滞后；帧序号由 presenter 内部维护，尚未输出到日志。以同条件对比端到端延迟中位数/P90、帧队列峰值、Qt 等待/绘制滞后及帧率；检查长时间运行、停止和再次连接，确认无花屏、明显卡顿或音画同步退化。若没有可重复的延迟改善，回退该显示策略。代码已接入并通过编译，SRS 实机验收仍待执行。
