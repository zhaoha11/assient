# 采集和编码的低延迟优化

## 1. 文档目标

本文只讨论以下视频发送链路的低延迟优化：

```text
Windows 桌面采集（gdigrab）
  -> BGRA 原始帧
  -> H.264 编码
  -> RTMP 视频帧发送
```

本文不修改拉流、解码、渲染、音频、信令或 RTMP 服务器逻辑。

优化目标：

1. 采集到新画面后立即编码，消除固定轮询带来的额外等待。
2. 不重复编码同一张采集帧。
3. 不在互斥锁保护下复制整张 BGRA 图像。
4. 编码跟不上时保留最新画面，而不是累积历史帧。
5. 统一采集帧率、编码帧率、GOP 和时间戳语义。
6. 用可测量的数据验证延迟变化，不预先承诺具体收益。

### 1.1 本轮确定方案

第一版明确采用以下边界，不在实施过程中临时切换方案：

```text
三缓冲池存储：BGRA
采集线程职责：采集、整理为紧凑 BGRA、发布最新帧
编码线程职责：BGRA -> YUV420P、H.264 编码、立即发送
```

色彩空间转换继续由现有编码线程完成，不移动到采集线程。这样可以保持采集线程轻量，避免 `sws_scale()` 阻塞下一次桌面采集，同时也能减少第一版的接口和线程职责变更。

YUV420P 三缓冲具有更小的缓冲池，但只作为后续有测量依据时的备选实验，不属于本轮实施范围。

## 2. 当前实现与问题

相关文件：

- `ECloudAssistant/Pusher/capture/GDISreenScapture.{h,cpp}`
- `ECloudAssistant/Pusher/RtmpPushManager.{h,cpp}`
- `ECloudAssistant/Codec/H264Encoder.{h,cpp}`
- `ECloudAssistant/Codec/VideoEncoder.{h,cpp}`

### 2.1 三套节拍不一致

当前参数为：

```text
gdigrab 采集帧率：25 FPS
H.264 编码器配置：30 FPS
EncodeVideo 循环周期：30 ms，约等于 33.3 次/秒
```

`30 ms` 不等于 `30 FPS`：

```text
1000 / 30 FPS = 33.33 ms/帧
1000 / 30 ms  = 33.33 FPS
```

25 FPS 采集最多只能产生每秒 25 张不同画面。编码线程以约 33.3 次/秒读取最新帧时，会重复取得并编码部分旧画面。这样会消耗 BGRA 拷贝、颜色转换、H.264 编码和网络带宽，但不会增加有效画面信息。

### 2.2 锁内执行整帧内存操作

当前采集线程在 `GDIScreenCapture::Decode()` 中持有 `mutex_`，然后执行：

```text
分配 rgba_frame_ 内存
逐行复制整张 BGRA 图像
```

当前编码线程在 `GDIScreenCapture::CaptureFrame()` 中持有同一把锁，然后通过 `rgba.assign(...)` 再复制一次整张图像。

以 1920x1080 BGRA 为例，一帧紧凑数据约为：

```text
1920 * 1080 * 4 = 8,294,400 bytes，约 7.9 MiB
```

锁内处理的数据量较大，采集线程和编码线程可能互相等待。逐帧分配内存还会增加耗时抖动。

### 2.3 固定轮询增加等待

采集线程和 `EncodeVideo()` 线程分别维护自己的休眠节拍。屏幕变化可能先等待下一次采集，再等待下一次编码轮询。

只考虑调度周期、暂不计算编码和网络耗时，当前理论等待范围约为：

```text
等待采集：0～40 ms
等待编码轮询：0～30 ms
```

两个线程的相位不固定，因此不能把该范围直接当作实际端到端延迟；它只说明当前设计存在可以移除的二次等待。实际收益必须通过时间戳测量确认。

### 2.4 当前 PTS 默认值存在语义问题

`VideoEncoder::Encode()` 的 `pts` 参数是 `quint64`，默认值为 0，而实现中使用：

```cpp
out_frame->pts = pts >= 0 ? pts : pts_++;
```

无符号整数恒大于等于 0，因此不传 PTS 时不会进入 `pts_++` 分支。采集和编码节拍改造时应同步明确 PTS 来源，避免继续依赖该默认参数。

## 3. 目标结构

采用单生产者、单消费者的三缓冲结构：

```text
采集线程
  -> 写入 back（采集线程独占，不加锁）
  -> 短临界区交换 back 与 middle
  -> 通知条件变量

编码线程
  -> 等待新帧通知
  -> 短临界区交换 front 与 middle
  -> 读取 BGRA front（编码线程独占，不加锁）
  -> BGRA 转 YUV420P
  -> H.264 编码
  -> 立即发送
```

三个缓冲区的职责：

| 缓冲区 | 格式 | 所有者 | 用途 |
| --- | --- | --- | --- |
| `back` | BGRA | 采集线程 | 写入当前正在采集的画面 |
| `middle` | BGRA | 交换区 | 保存最新发布、尚未被编码线程取得的画面 |
| `front` | BGRA | 编码线程 | 编码线程当前正在转换和编码的画面 |

当编码速度低于采集速度时，采集线程继续交换 `back` 和 `middle`，旧的待编码画面会被覆盖，`middle` 始终趋向保存最新画面。`front` 在当前编码结束前不会被采集线程访问。

该语义适合远程桌面：优先传递最新状态，不为已经过时的中间画面增加排队延迟。

## 4. 数据结构建议

缓冲区在采集尺寸确定后一次性分配：

```cpp
struct CaptureFrameBuffer
{
    std::vector<uint8_t> data;
    uint32_t width = 0;
    uint32_t height = 0;
    uint32_t stride = 0;
    uint32_t validBytes = 0;
    uint64_t sequence = 0;
    std::chrono::steady_clock::time_point capturedAt;
};

std::array<CaptureFrameBuffer, 3> frameBuffers_;

size_t frontIndex_ = 0;
size_t middleIndex_ = 1;
size_t backIndex_ = 2;

std::mutex frameMutex_;
std::condition_variable frameReady_;
bool hasNewFrame_ = false;
bool stopped_ = false;
```

固定内存池由 `GDIScreenCapture` 独占生命周期，不需要 `std::shared_ptr`。使用索引交换可以避免引用计数开销，并让缓冲区所有权更清晰。

如果分辨率在采集期间不会改变，每个 `data` 只在初始化时执行一次 `resize()`：

```cpp
const uint32_t packedStride = width * 4;
const uint32_t bufferSize = packedStride * height;
```

若运行时允许分辨率变化，应停止当前采集和编码线程，重新分配三块缓冲区后再恢复，不要在正常逐帧路径中动态扩容。

## 5. 线程交换流程

### 5.1 采集线程发布新帧

```cpp
CaptureFrameBuffer& writeBuffer = frameBuffers_[backIndex_];

// 锁外完成整帧写入。
CopyFrameToBuffer(decodedFrame, writeBuffer);
writeBuffer.sequence = ++captureSequence_;
writeBuffer.capturedAt = std::chrono::steady_clock::now();

{
    std::lock_guard<std::mutex> lock(frameMutex_);
    std::swap(backIndex_, middleIndex_);
    hasNewFrame_ = true;
}

// 在解锁后通知，减少被唤醒线程再次等待互斥锁的概率。
frameReady_.notify_one();
```

锁内只交换索引并修改状态，不执行分配、整帧复制或编码。

### 5.2 编码线程取得最新帧

```cpp
std::unique_lock<std::mutex> lock(frameMutex_);

frameReady_.wait(lock, [this]() {
    return hasNewFrame_ || stopped_;
});

if(stopped_)
{
    return;
}

std::swap(frontIndex_, middleIndex_);
hasNewFrame_ = false;

lock.unlock();

// front 在本次编码完成前由编码线程独占。
const CaptureFrameBuffer& frame = frameBuffers_[frontIndex_];
EncodeAndPush(frame);
```

条件变量必须使用谓词，以处理虚假唤醒并防止停止流程永久等待。

### 5.3 停止流程

停止时应在同一把状态锁下设置停止标志，然后唤醒编码线程：

```cpp
{
    std::lock_guard<std::mutex> lock(frameMutex_);
    stopped_ = true;
}
frameReady_.notify_all();
```

资源释放顺序：

```text
设置停止标志
  -> 唤醒并等待编码线程退出
  -> 停止并等待采集线程退出
  -> 释放编码器、FFmpeg 上下文和三块缓冲区
```

编码器不得在函数返回后继续异步持有 `front.data.data()`。当前软件编码调用是同步路径；如果未来切换为异步硬件编码，必须重新定义缓冲区归还时机。

## 6. 图像复制与色彩转换规则

### 6.1 BGRA 缓冲区复制

不要使用 `AVFrame::pkt_size` 作为解码后 BGRA 图像的缓冲区大小。目标缓冲区大小应根据像素布局计算。

若内存池使用紧凑 BGRA：

```cpp
const uint32_t rowBytes = width * 4;
buffer.stride = rowBytes;
buffer.validBytes = rowBytes * height;

for(uint32_t y = 0; y < height; ++y)
{
    std::memcpy(buffer.data.data() + y * rowBytes,
                frame->data[0] + y * frame->linesize[0],
                rowBytes);
}
```

不能把源 `linesize[0]` 直接当作目标每行有效字节数，因为 FFmpeg 的行跨度可能包含对齐填充。

还应在初始化时记录并检查采集帧的实际像素格式。编码器当前按 `AV_PIX_FMT_BGRA` 接收输入，采集端不应在未验证时把同一内存声明为 `AV_PIX_FMT_RGBA`。本次改造应通过日志或断言确认 gdigrab 实际输出格式，再统一采集缓冲区和编码器的格式参数。

### 6.2 色彩转换保留在编码线程

当前 `VideoEncoder::Encode()` 通过 `VideoConverter::Convert()` 完成 BGRA 到 YUV420P 的转换。本轮保留该线程边界：

```text
采集线程：av_read_frame -> BGRA 帧整理 -> 发布 back
编码线程：取得 front -> BGRA 转 YUV420P -> H.264 编码 -> PushVideo
```

这样做的主要原因不是 BGRA 缓冲更节省内存，而是让采集线程可以尽快返回下一次 `av_read_frame()`。如果把 `sws_scale()` 放进采集线程，色彩转换耗时会直接串行叠加到采集周期上，高分辨率或 CPU 负载波动时可能降低实际采集速率并增加画面年龄。

1080P 三缓冲的容量对比如下：

| 格式 | 单帧字节数 | 三缓冲字节数 |
| --- | ---: | ---: |
| BGRA | 8,294,400 | 24,883,200 |
| YUV420P | 3,110,400 | 9,331,200 |

YUV420P 缓冲区容量比 BGRA 低 62.5%，但该比例不能直接解释为总内存总线流量也降低 62.5%，因为色彩转换仍需读取 BGRA 并写入 YUV420P。

只有在第一版完成后，同时满足以下条件，才考虑单独进行 YUV420P 三缓冲 A/B 实验：

1. 测得 BGRA 到 YUV420P 转换耗时稳定且占比较高。
2. 把转换加入采集路径后，实际采集 FPS 和采集间隔抖动没有恶化。
3. 实测端到端延迟下降，而不只是内存占用下降。

后续实验若采用 YUV420P 三缓冲，还必须让编码器直接接收 Y、U、V 平面及对应 `linesize`，真正绕过现有 `VideoConverter`；只把缓冲区换成 YUV、随后再次转换没有意义。

## 7. 帧率和时间戳策略

### 7.1 单一帧率配置

建议先选择 30 FPS 作为低延迟实验值，并让一项配置同时驱动：

```text
gdigrab framerate = 30
H.264 framerate   = 30
H.264 time_base   = 1/30
GOP               = 30
```

不再保留独立的 `30 ms` 编码发送节拍。编码线程由新帧条件变量驱动，编码完成后立即发送。

如果运行测试显示 30 FPS 下 CPU 使用率过高，可以把同一配置整体调整为 25 FPS：

```text
gdigrab framerate = 25
H.264 framerate   = 25
H.264 time_base   = 1/25
GOP               = 25
```

不要只修改其中一处。

### 7.2 只保留一个采集时钟

当前采集线程既向 gdigrab 设置帧率，又在 `run()` 中调用 `sleep_for(1000 / framerate_)`。

阶段一实测采集稳定在约 12.5 FPS，与 gdigrab 的 25 FPS 限速和外层 40 ms 休眠叠加高度一致。因此把删除外层固定休眠提前为阶段 1.5 的单变量实验，让 `av_read_frame()` 暂时成为唯一采集节拍。若实测不能恢复到接近 25 FPS，再检查 `av_read_frame()` 的阻塞时间；不要同时引入其他节拍器。

### 7.3 编码 PTS

阶段三 B 采用简单、可验证的单调编码 PTS：

```cpp
outFrame->pts = pts_++;
```

同时删除无符号可选 PTS 的错误哨兵语义。若以后需要让编码 PTS 精确反映采集间隔，再把 `capturedAt` 换算到编码器 `time_base`；本阶段不同时引入该复杂度。

RTMP 当前使用自身的单调经过时间生成消息时间戳。本方案不改变 RTMP 协议和消息结构。

## 8. 接口调整建议

当前接口：

```cpp
bool CaptureFrame(FrameContainer& rgba,
                  quint32& width,
                  quint32& height);
```

该接口强制把内部帧复制到调用方 `vector`。建议替换为阻塞取得内部 `front` 只读视图的接口，例如：

```cpp
struct CaptureFrameView
{
    const uint8_t* data = nullptr;
    uint32_t width = 0;
    uint32_t height = 0;
    uint32_t stride = 0;
    uint32_t size = 0;
    uint64_t sequence = 0;
    std::chrono::steady_clock::time_point capturedAt;
};

bool WaitLatestFrame(CaptureFrameView& frame);
```

生命周期约束必须写进接口注释：

```text
返回的数据由 GDIScreenCapture 持有；
在下一次 WaitLatestFrame() 或 Close() 前有效；
调用方不得保存、释放或异步使用该指针。
```

`RtmpPushManager::EncodeVideo()` 调整为：

```text
等待最新帧
  -> 编码一次
  -> 有编码包则立即 PushVideo
  -> 再等待下一张新帧
```

删除该函数中的固定 `sleep_for()` 和独立帧率变量。

## 9. 分阶段实施计划

### 阶段一：建立基线

只增加低频统计，不改变媒体行为：

- 采集帧 `sequence`。
- 每秒实际采集帧数。
- 每秒实际编码帧数。
- 重复编码帧数。
- 采集完成到编码开始的等待时间。
- BGRA 到 YUV420P 的转换耗时。
- 单帧编码耗时。

日志应每秒汇总一次，不要逐帧输出，以免日志本身干扰时序。

验证：使用相同分辨率、场景、网络和播放器，记录多组端到端延迟及上述统计。

#### 阶段一当前结果（2026-09-17）

- 测试分辨率：1920x1080。
- 实际采集约 12.5 FPS，实际编码约 25 FPS。
- 每秒约有 11～14 个重复编码帧，`skip = 0`；基本每张新画面被编码两次。
- 采集完成到编码开始平均等待约 33～39 ms，最大约 66～81 ms。
- BGRA 转 YUV420P 平均约 6.7～7.5 ms，软件 H.264 编码平均约 2.1～2.5 ms。
- 结果与“gdigrab 25 FPS 限速叠加采集线程 40 ms 休眠，导致实际约 12.5 FPS”高度一致。
- 推流停止后状态恢复为 `IDLE`，程序正常退出。
- 第一条 `[PIPE-STATS]` 存在统计周期初始化偏差，分析时以第二条之后的数据为准。

阶段一剩余任务：

1. 第一条统计的周期初始化偏差已在阶段 1.5 开始前修正。
2. 仍需在相同条件下补充多组端到端视觉延迟样本。
3. AAC 的 64 bps/64 kbps 单位问题单独处理，不混入本轮视频实验。
4. 阶段 1.5 已完成；第二阶段已实施，见下。

### 阶段 1.5：单一采集时钟实验（已完成，2026-09-17）

只修改一个变量：

```text
删除 GDIScreenCapture::run() 中的 40 ms sleep_for
```

保持以下条件不变：

- gdigrab 仍配置为 25 FPS。
- 编码器仍配置为 30 FPS、GOP 30。
- `EncodeVideo()` 仍使用原来的 30 ms 轮询。
- 保留原来的锁、整帧复制、码率和 PTS 行为。

验证：

- `captureFps` 从约 12.5 上升到接近 25。
- `dup`、`waitAvgUs` 和 `waitMaxUs` 相比阶段一明显下降。
- `convertAvgUs` 和 `encodeAvgUs` 保持在相近范围。
- 使用相同分辨率、场景、网络和播放器重新记录端到端延迟。

#### 阶段 1.5 实验结果

- 实际采集约 24～26 FPS，六个完整周期平均约 24.9 FPS。
- 实际编码约 22～25 FPS，六个完整周期平均约 23.9 FPS。
- 重复编码降至每秒 0～3 帧；序号跳跃为每秒 1～4 帧。
- 平均等待降至约 17～23 ms，最大等待约 40～52 ms。
- BGRA 转 YUV420P 平均约 6.7～7.4 ms，软件 H.264 编码约 2.5～3.2 ms，和阶段一基本一致。
- 首周期统计偏差已经修正，本次第一条 `[PIPE-STATS]` 可以计入结果。

结论：删除外层 40 ms 休眠后，采集从约 12.5 FPS 恢复到约 25 FPS，确认双重限速是阶段一采集减半的主要原因。重复编码和采集到编码的等待均明显下降；剩余的少量 `dup`、`skip` 和约 40～52 ms 最大等待，符合采集与编码仍使用独立轮询时钟、锁内整帧复制尚未移除的现状。

阶段 1.5 验收通过。三缓冲与条件变量按后续指令在阶段二实施。

### 阶段二：三缓冲与新帧通知（核心验收通过，2026-09-17）

目的：消除采集和编码之间的固定轮询等待、锁内整帧复制与逐帧大块内存分配。通过三缓冲明确采集写、编码读和备用交换的所有权，并在新帧到达时立即唤醒编码线程，使编码线程只处理新画面；处理不过来时保留最新帧，不累积旧帧延迟。本阶段保持现有编码器帧率、GOP、码率、PTS和RTMP行为不变。

实施：

- 初始化时分配三块固定 BGRA 缓冲区。
- 采集线程在锁外写 `back`。
- 采集和编码线程只在短临界区交换索引。
- 使用条件变量唤醒编码线程。
- 删除 `CaptureFrame()` 的整帧输出复制。
- 删除 `EncodeVideo()` 的固定 30 ms 轮询。
- 保留 `VideoEncoder::Encode()` 在线程内完成 BGRA 到 YUV420P 转换。
- 本阶段继续保持 25 FPS，不同时引入 30 FPS 变更。

验证：

- 编码帧序号严格递增，不重复。
- 编码线程落后时允许序号跳跃，但不会回退。
- 连续运行过程中内存占用保持稳定。
- 快速变化测试画面无撕裂、错行和颜色通道错误。
- 建立、关闭、再次建立推流均正常。

#### 阶段二实现与结果（2026-09-17）

代码已完成并编译通过。1920x1080 运行结果：采集和编码均稳定在约 25 FPS，逐周期数量一致，`dup = 0`、`skip = 0`；采集发布到编码线程开始处理的平均等待约 27～39 微秒，最大约 37～230 微秒；BGRA 转 YUV420P 约 6.8～7.2 ms，软件 H.264 编码约 1.7～2.5 ms。

结论：三缓冲和新帧通知已消除固定轮询等待、锁内输出复制与重复编码，阶段二核心指标验收通过。仍需补充关闭/重连和长时间运行验证，阶段三尚未开始。

采集端（`GDISreenScapture`）：

- 删除 `CaptureFrameMeta`、`CaptureFrame()`、`rgba_frame_`、`frame_size_` 和原来的 `mutex_`，改由三块固定 `CaptureFrameBuffer` 承载整帧。
- 新增 `CaptureFrameView`（编码线程持有的只读视图）与 `WaitLatestFrame()`；`Init()` 里一次性按 `av_image_get_linesize(kCapturePixelFormat, width, 0)` 分配三块紧凑 BGRA 缓冲。
- `Decode()` 在锁外把解码帧按行复制进 `back`，锁内只 `std::swap(back, middle)` 并置 `hasNewFrame_`，解锁后 `notify_one()`。
- `WaitLatestFrame()` 在谓词 `hasNewFrame_ || stopped_` 上等待，`stopped_` 在交换索引之前判断，停止时不改动索引。
- 所有权不变式：三个索引两两不等且覆盖 {0,1,2}，采集只动 {back, middle}，编码只动 {front, middle}，因此锁外写入的 `back` 恒不等于编码线程刚换成的 `front`，三块足够。
- 新增 `RequestStop()`：幂等、不 join、不释放，只置 `stopped_` 并 `notify_all()`；`Close()` 内部先调它，所以单独调用 `Close()` 不会死锁。
- `stop_`、`is_initialzed_` 改为 `std::atomic<bool>`，消除既有的跨线程数据竞争。
- 删除死代码 `codec_context_->pix_fmt = AV_PIX_FMT_RGBA;`（被下一行 `avcodec_parameters_to_context()` 无条件覆盖），改为在首个解码帧上打印实测格式与 `linesize[0]`。

停止顺序（`RtmpPushManager::Close()`，防死锁的关键）：`exit_ = true` → `isConnect = false` → `screen_Capture_->RequestStop()` → `StopEncoder()`（join 音频、视频线程）→ 关闭 pusher → `StopCapture()`（`screen_Capture_->Close()` 停采集线程并释放三块缓冲）。缓冲池释放必须晚于视频线程 join；`RequestStop()` 只依赖采集类自己的 `stopped_`，不读 `exit_`，采集类不反向依赖推流器。
%%%%%%死锁：意思就是主线程需要调用join去回收子线程，但是子线程由于判断条件或者条件变量需要等待主线程去执行，代码，但是，join是阻塞的，所以这里有问题

编码线程（`EncodeVideo()`）：删除 `static Timestamp`、局部 `fameRate` 和 `sleep_for()`，改为 `while(!exit_ && isConnect && capture) { capture->WaitLatestFrame(view); ... }`，完全由新帧通知驱动；退出时补一行 `[PIPE-STATS] encode thread exit, captured = ...`，用来把「停滞」和「死锁」区分开。BGRA→YUV420P 仍在编码线程内完成，线程边界不变。

顺带修正的编码器缺陷（`VideoEncoder`）：

- 转换器与 `rgba_frame_` 的 guard 原来拿输入尺寸比编码器尺寸，而 `Init()` 把编码器尺寸截成偶数，奇数宽度下该分支每帧成立，导致每帧重建 sws 上下文并对已分配帧重复调 `av_frame_get_buffer`（泄漏加未定义行为）。改为比较新增的 `sourceWidth_/sourceHeight_`，并在重新分配前先 `av_frame_unref()`。1920 下该缺陷是休眠的。
- 整帧 `memcpy` 改为按行复制：目标跨距取 `rgba_frame_->linesize[0]`（`av_frame_get_buffer(..., 32)` 会对齐到 32），源跨距取 `width * 4`。原写法只在 `width * 4` 能被 32 整除时正确。
- 像素格式统一为 `AV_Common.h` 里的 `kCapturePixelFormat`，采集端行跨度和 `H264Encoder::OPen()` 入参都由它派生。
- `H264Encoder::Encode` / `VideoEncoder::Encode` 的首个入参改为 `const quint8*`（`view.data` 直接传入，不需要 `const_cast`），并删除已由 `width * 4` 完全推导的 `size` 参数。

改动文件：`GDISreenScapture.{h,cpp}`、`RtmpPushManager.cpp`、`VideoEncoder.{h,cpp}`、`H264Encoder.{h,cpp}`、`AV_Common.h`。编译用 Qt MinGW 工具链，无新增警告。

统计结果符合目标：`dup` 和 `skip` 均为 0，`waitUs` 已降到微秒级并只反映条件变量唤醒延迟。注意 `ReportIfDue` 现在每轮就是一个新帧，采集停止产出时统计行也会停，不再是「每秒必有」。

`dup = 0` 与 `skip = 0` 同时出现，含义是采集和编码严格 1:1：每张新画面恰好编码一次，既无重复也无序号跨越。阶段 1.5 残留的 `dup` 0～3/秒、`skip` 1～4/秒全部消失，说明两个独立时钟的拍频已经消除。这比预期更好——原计划允许 `skip` 非零（编码偶尔落后），实际编码线程始终跟得上，这与算力余量一致：单帧 convert 约 6.7～7.5 ms 加 encode 约 2.5～3.2 ms，而 25 FPS 的预算是 40 ms。

附带含义：由于编码从不落后，「编码落后时丢弃旧画面而不是排队」这条路径本次没有被触发。该分支已实现，所有权不变式也推演过（锁外写入的 `back` 恒不等于编码线程刚换成的 `front`），但没有被实际观测。要压测它需要人为让编码落后，例如更重的画面或更低的 CPU。

尚待确认：连续数分钟内存是否稳定、快速变化画面无撕裂/错行/红蓝颠倒、停止再推流正常且出现 `encode thread exit` 日志（验证未死锁）。

### 阶段 2.5：统一提升到 30 FPS（核心运行指标通过）

目的：在阶段二三缓冲链路稳定后，把实际采集和编码处理速率从约 25 FPS 统一提升到 30 FPS，观察增加 20% 帧数后对采集、颜色转换、软件编码、CPU占用和端到端延迟的影响，确认 30 FPS 是否是当前 1920×1080 软件编码链路中性能与流畅度兼顾的合适档位。本阶段只验证帧率变化，不与 PTS、码率或编码器调整混在一起。

调整前状态：采集端配置为 25 FPS，H.264 编码器参数为 30 FPS；编码线程由新帧通知驱动，所以实际采集和编码都约为 25 FPS。现有单帧 `convert + encode` 约 8.5～9.7 ms，低于 30 FPS 的 33.3 ms 单帧预算，具备进入 30 FPS 受控实验的基础，但这不等同于已经确认整机 CPU、网络和端到端链路都有同等余量。

执行顺序：

1. 代码保持不变，先采集并记录当前 25 FPS 的同场景基线日志。
2. 收到并确认 25 FPS 日志后，再把采集和编码配置统一为 30 FPS；GOP 保持 30、B 帧保持 0。
3. 不同时修改码率、PTS、编码器、分辨率或三缓冲实现。
4. 使用相同桌面场景、运行时长、网络和播放器重复测试，比较 25 FPS 与 30 FPS。

重点对比：

- `captureFps`、`encodeFps` 是否从约 25 提升并稳定在约 30。
- `dup` 是否保持为 0，`skip` 是否保持为 0 或仅偶发出现。
- `waitAvgUs`、`waitMaxUs` 是否仍保持低位。
- `convertAvgUs`、`encodeAvgUs` 是否稳定，二者之和是否持续低于 33.3 ms。
- 整机 CPU 占用、快速变化画面的码率和端到端视觉延迟是否可接受。
- 停止、重连和再次推流是否正常，且没有画面撕裂、错行或颜色异常。

#### 25 FPS 基线结果

本次 1920×1080 日志中，第一周期仍带有启动影响：编码数比采集数多 1，`waitAvgUs = 954`、`waitMaxUs = 21303`，不计入稳态均值。后续三个完整周期中，采集和编码均稳定在约 25 FPS，每周期数量一致，`dup = 0`、`skip = 0`；平均等待约 29～32 微秒，最大等待约 41～63 微秒；BGRA 转 YUV420P 约 6.6～6.8 ms，软件 H.264 编码约 1.8 ms，二者合计约 8.5 ms。

结论：25 FPS 基线稳定，三缓冲交接没有重复或跳帧，单帧转换与编码耗时明显低于 30 FPS 的 33.3 ms 预算，可以进入统一 30 FPS 的受控调整。当前只记录基线。

#### 30 FPS 代码改动与结果（2026-09-18）

关键发现：编码器侧本来就是 30 FPS。`RtmpPushManager::Init()` 传入的编码帧率是 30，`VideoEncoder` 的 `time_base = 1/30`、`framerate = 30/1`、`gop_size = 30`、`max_b_frames = 0` 全部是目标值。真正把整条链路压在约 25 FPS 的只有采集端一个值：`GDISreenCapture` 的 gdigrab `framerate` 选项原来是 25。阶段二之后编码线程由新帧通知驱动、不再是限速方，所以把 gdigrab 提到 30，采集和编码会一起到 30。

改动（按文档 §7.1「单一帧率配置」统一口径，与 `kCapturePixelFormat` 同构）：

- `AV_Common.h` 新增 `constexpr qint32 kTargetFramerate = 30`，作为唯一帧率口径。注释里写明 GOP 不在其中——编码器的 `gop_size` 固定 30，不随帧率派生。（该注释已在阶段 2.6 随 `gop_size` 改为读取 `config_.video.gop` 一起更新，当前文字是「约 1 秒的 GOP 由它派生」。）
- `GDISreenCapture` 的 `framerate_` 由 `25` 改为 `kTargetFramerate`，它只用于 gdigrab 的 `framerate` 选项。
- `RtmpPushManager::Init()` 的 `OPen(..., 30, 80000, kCapturePixelFormat)` 改为传入 `kTargetFramerate`。数值不变（本来就是 30），所以编码器的实际配置没有变化，仍满足「不同时修改编码器」。

未触碰：码率 80000 kbps、`gop_size = 30`、`max_b_frames = 0`、`ultrafast`/`zerolatency`、`kCapturePixelFormat`、三缓冲实现、PTS 语义（留待阶段三）。

运行结果：五个周期的采集和编码平均约 30.0 FPS，累计 153 帧均保持 1:1，`dup = 0`、`skip = 0`；平均等待约 34 微秒，最大等待多数低于 0.1 ms、单次 0.5 ms；BGRA 转 YUV420P 平均约 6.93 ms，软件 H.264 编码约 2.08 ms，合计约 9.01 ms，低于 30 FPS 的 33.3 ms 单帧预算。

结论：30 FPS 下未出现重复、跳帧或编码积压，阶段 2.5 核心流水线指标通过。仍需补充整机 CPU、实际码率、端到端视觉延迟、长时间运行和停止重连验证。

### 阶段 2.6：60 FPS 压力测试（未达到目标，实际约 40 FPS）

目的：在 30 FPS 已稳定通过的基础上，把采集和编码统一提升到 60 FPS，验证当前 1920×1080 软件编码链路的性能上限，并观察 CPU、跳帧和端到端延迟变化。60 FPS 更适合与常见 60 Hz 桌面刷新节奏对比，但单帧预算只有约 16.7 ms，每秒处理量是 30 FPS 的两倍。当前约 9.01 ms 的转换加编码耗时具备实验基础，但余量明显小于 30 FPS。

实施：把 `kTargetFramerate` 从 30 调整为 60，同时把 `VideoEncoder.cpp:64` 的硬编码 `gop_size = 30` 改为读取 `config_.video.gop`；`H264Encoder::OPen()` 已按目标帧率设置该字段，因此本轮会同步得到 GOP 60，继续保持约 1 秒一个 GOP。码率、B 帧、分辨率、PTS 和三缓冲实现保持不变。

验证：首要判据是 `captureFps` 接近 60，并且采集与编码逐周期保持 1:1、`skip = 0`；若持续出现 `skip` 或编码数落后于采集数，则说明 60 FPS 无法稳定处理。`dup` 应继续保持 0。`convertAvgUs + encodeAvgUs` 低于 16.7 ms 只作为必要参考，不单独作为通过依据，因为当前统计没有计入四项开销：gdigrab 读取与解码、解码帧复制到三缓冲 `back`、`front` 复制到编码器输入帧、`PushVideo` 中的封装/复制与 RTMP 发送调用。因此还要观察整机 CPU、实际码率和端到端视觉延迟；若 CPU 长期过高或延迟反而增加，则保留 30 FPS 作为稳定配置。

#### 代码改动（2026-09-18）

已落地两处，均不改变 30 FPS 下的行为：

- `VideoEncoder.cpp` 的 `gop_size` 由硬编码 `30` 改为读取 `config_.video.gop`。`H264Encoder::OPen()` 已按目标帧率设置该字段，所以 30 FPS 下取值仍为 30（等价 no-op），到 60 FPS 会自动变成 60，保持约 1 秒一个 GOP。全项目只有 `H264Encoder::OPen()` 一个构造点写入该字段，不存在留 0 的调用方。
- `kTargetFramerate` 已从 30 调整为 60，采集帧率、编码器时间基和 GOP 统一为 60。

#### 60 FPS 运行结果

五个周期的采集和编码平均约 40.1 FPS，累计 202 帧保持 1:1，`dup = 0`、`skip = 0`；平均等待约 42 微秒，最大等待约 0.15～0.55 ms；BGRA 转 YUV420P 平均约 6.71 ms，软件 H.264 编码约 2.11 ms，合计约 8.81 ms。

结论：配置已经是 60 FPS / GOP 60，但实际采集只达到约 40 FPS，因此未通过“接近 60 FPS”的验收。编码帧数始终与采集帧数一致且没有跳帧，说明三缓冲和编码线程能够跟上采集端实际提供的画面；现有日志只能把限制范围定位到编码线程之前，尚不能区分 gdigrab、桌面捕获或系统调度中的具体原因。

#### 构建依赖的既有缺陷（已修复，影响本阶段所有测量）

`build/Desktop_Qt_6_10_1_MinGW_64_bit-Debug/Makefile.Debug` 的对象依赖表**不完整**：62 条对象规则中只有 27 条把 `Codec/AV_Common.h` 列为前置依赖。`debug/GDISreenScapture.o` 的规则是在阶段二给它加 `#include "AV_Common.h"` **之前**生成的，因此修改该头文件**不会**重编译它。

后果是本次实测到的：把 `kTargetFramerate` 改为 60 时，`RtmpPushManager.o` 重编译了，而 `GDISreenScapture.o` 停留在旧值，产生「编码器 60 / 采集 30」的不一致产物。该产物链接成功、文件名和时间戳都正常，若直接拿去测会得到一组无意义的帧率数据。

已用 `qmake.exe -o Makefile ..\..\ECloudAssistant.pro -spec win32-g++ CONFIG+=debug CONFIG+=qml_debug` 重新生成 Makefile，`GDISreenScapture.o` 的规则现已包含 `AV_Common.h`；重建后只有该文件被重编译，验证修复生效。

注意两点：`qmake_all` 在子 Makefile 里是**空目标**，不能用来重新生成；不要传 `-o Makefile.Debug`，否则 qmake 会把它当成顶层名，把真正的规则写到 `Makefile.Debug.Debug` 并破坏原有布局。此缺陷只影响命令行构建，Qt Creator 会自行重新生成 Makefile。



















### 阶段 2.7：640×480 小区域采集实验（已完成）

目的：保持 60 FPS、GOP 60 和现有线程结构不变，只把 gdigrab 的采集区域从 1920×1080 缩小为主屏左上角 640×480，用一次变量实验判断约 40 FPS 的限制是否主要随像素量变化。

判据：若 `captureFps` 明显接近 60 且 `encodeFps` 保持 1:1、`skip = 0`，说明整屏回读或整帧复制等像素相关开销是主要限制；若仍停留在约 40 FPS，则更偏向 GDI 调用、虚拟机调度或定时器等固定每帧开销。编码器会自动使用采集器返回的 640×480 尺寸。本阶段不加入分段计时，也不修改码率、PTS 或三缓冲实现。

结果：按四个字段完整的统计周期计算，采集和编码平均约 54.8 FPS，范围为 51.0～56.8 FPS，累计 222 帧保持 1:1，`dup = 0`、`skip = 0`。平均交接等待约 28 微秒，最大等待为 49～268 微秒；颜色转换平均约 1.10 ms，软件编码平均约 0.52 ms，合计约 1.62 ms。最后一个未完整显示的周期为 55.3 FPS，与前述范围一致，但不计入均值。

结论：相较 1920×1080 下约 40.1 FPS，640×480 提升到约 54.8 FPS，增幅约 36.5%，证明整屏回读、整帧复制等像素量相关开销是重要限制；但小区域仍未稳定达到 60 FPS，说明它不是唯一限制，仍有 GDI 固定调用、系统/虚拟机调度或同机资源竞争等剩余开销。编码端全程与采集端 1:1 且无跳帧，约 1.62 ms 的转换加编码耗时也表明编码线程不是本轮上限。实验结束后应恢复主屏完整区域采集。

最终处置：阶段 2.7 实验完成后，代码已恢复为主屏完整区域采集；当前设备为 1920×1080。统一目标帧率恢复为 30 FPS，GOP 随配置恢复为 30。Debug 构建和链接通过，后续以阶段 2.5 已验证的 1080p/30 FPS 作为稳定配置。

| 声道数 | 运行时读取默认设备；当前代码注释预期双声道 | 通过 `av_channel_layout_default` 建立声道布局 |
| 采集 PCM 格式 | 16-bit S16 | 采集 PCM 格式：**协商输出 16-bit S16LE（由 Windows 音频引擎完成位深转换，声卡硬件原生格式不固定）** |
| 编码器 | AAC | 通过 `AV_CODEC_ID_AAC` 查找 |
| 编码采样格式 | FLTP | 编码前由 S16 重采样为 FLTP，采样率和声道数不变 |
| 音频码率 | 64 kbps，即 64,000 bit/s | `AACEncoder` 将接口传入的 kbps 乘以 1000 后写入 `AVCodecContext::bit_rate` |
| 全局头 | 开启 | `AV_CODEC_FLAG_GLOBAL_HEADER`，用于生成 AAC AudioSpecificConfig |

注意：视频的 12 Mbps 是编码器目标/上限配置，不等于静态桌面场景一定会产生 12 Mbps 的实际 RTMP 流量；音频码率已按接口约定正确换算为 64 kbps。



**落地结论**：如果未来在 1080P 下必须跑满 60 FPS，仅靠优化现有的 CPU 软拷贝代码已逼近极限，唯一出路是抛弃 GDI，转向 **DXGI Desktop Duplication（GPU 显存直接共享）**。

### 阶段 2.8：H.264 码率与 Level 兼容性收敛（核心运行指标通过）

目的：解决当前 80 Mbps 使编码器自动升到 H.264 Level 5.0、部分硬件解码器可能不兼容的问题，在保持 1080p/30 FPS 和低延迟设置不变的前提下，将码率与 Level 收敛到更通用的范围。

推荐目标参数：

| 参数 | 当前配置 | 阶段 2.8 目标 |
| --- | --- | --- |
| 分辨率 | 1920×1080 | 不变 |
| 帧率 | 30 FPS | 不变 |
| 视频码率 | 80 Mbps | 12 Mbps |
| Profile | 未显式设置，日志为 Constrained Baseline | 显式设置 `baseline` |
| Level | 未显式设置，日志为 5.0 | 显式设置 `4.0` |
| GOP | 30 帧 | 不变 |
| B 帧 | 0 | 不变 |
| preset / tune | `ultrafast` / `zerolatency` | 不变 |

计划改动：把 `RtmpPushManager.cpp` 传入的视频码率从 `80000` 调整为 `12000` kbps，并在 `VideoEncoder.cpp` 打开编码器前设置 `profile=baseline`、`level=4.0`。本阶段不修改帧率、分辨率、GOP、PTS、采集和三缓冲实现。

验证：编码日志应显示 Constrained Baseline / Level 4.0；采集与编码继续稳定在 30 FPS、`skip = 0`；快速滚动、视频播放和文字界面无明显画质下降，并在目标设备上确认硬件解码正常。若 12 Mbps 画质不足，可单独测试 16 Mbps。

当前状态：代码已修改（2026-09-18），Debug 构建与链接通过；核心运行指标通过，目标设备硬件解码和主观画质仍待确认，尚未提交代码。

#### 代码改动（2026-09-18）

- `Pusher/RtmpPushManager.cpp:105`：`OPen(...,kTargetFramerate,80000,...)` 改为 `12000`，即 12 Mbps。`H264Encoder::OPen` 内部仍做 `bitrate * 1000`，因此四个码率控制字段同步落到 12,000,000，无其它调用点需要修改。
- `Codec/VideoEncoder.cpp:` 在 `avcodec_open2` 之前新增 `codecContext_->profile = FF_PROFILE_H264_BASELINE;` 与 `codecContext_->level = 40;`（期间试过改为 `MAIN`，见下方「profile 最终取 Baseline」）。

两点实现细节已实测确认（对照 FFmpeg n6.0 `libavcodec/libx264.c`）：

1. **不能用 `FF_PROFILE_H264_CONSTRAINED_BASELINE`**。libx264 的 profile 映射只覆盖 `FF_PROFILE_H264_BASELINE`、`MAIN`、`HIGH`、`HIGH_10`、`HIGH_422`、`HIGH_444`，Constrained Baseline 落到 `default: break;`，profile 字符串不会被设置——写它会编译通过、运行无警告、编码器却仍按自己的默认档位输出。选择 `FF_PROFILE_H264_BASELINE` 后由 x264 施加 baseline 约束，配合现有的 `max_b_frames = 0` 与 `ultrafast`（含 `--no-cabac`），实际码流仍是 Constrained Baseline，日志字符串与改动前一致，变化只体现在 Level 上。
2. **Level 4.0 与帧率强耦合，1080p 下只到 30 FPS**。Level 4.0 的 `MaxMBPS` 为 245760，1920×1080 每帧 120×68 = 8160 个宏块，30 FPS 时 8160 × 30 = 244800，仅剩 0.4% 余量；`MaxFS` 8192 ≥ 8160 与 `MaxBR`、`MaxCPB` 均满足。结论是当前配置合法，但只要再提高帧率（例如阶段 2.6/2.7 试过的 60 FPS）就会超出 Level 4.0 的上限，必须同步提高 level。该约束已写在 `VideoEncoder.cpp` 的赋值处。

副作用（预期的收益）：码率从 80 Mbps 降到 12 Mbps 后单帧字节数下降约 85%，网络串行化时间与拥塞风险同步下降，对阶段 2.5 测得的端到端延迟是正向的；80 Mbps 在 100 Mbps 局域网下本就接近链路上限，是潜在的抖动来源。`rc_buffer_size` 仍等于码率，VBV 时长（1 秒）不变。

#### 运行结果

编码器日志已确认 `profile Constrained Baseline, level 4.0`，并显示 `bitrate=12000`、`vbv_maxrate=12000`、`vbv_bufsize=12000`、GOP 30、B 帧 0，说明推荐参数已实际生效。本次短时统计的编码输出约为 12.53 Mbps；由于未启用 filler，实际输出不要求严格等于 12 Mbps。

三个字段完整的周期合计采集并编码 92 帧，平均约 30.0 FPS，始终保持 1:1，`dup = 0`、`skip = 0`；平均交接等待约 30 微秒，最大等待为 61～84 微秒；颜色转换平均约 7.00 ms，软件编码平均约 2.42 ms，合计约 9.43 ms。停止时出现 `encode thread exit` 和受控端回到 `IDLE`，未发生停止死锁。

结论：12 Mbps、Baseline、Level 4.0 没有破坏现有 1080p30 采集编码流水线，阶段 2.8 的码流参数和核心运行指标通过。仍需在目标设备上确认硬件解码实际启用，并观察快速滚动、视频播放和文字边缘的主观画质；在完成这两项前，不宣称兼容性验收全部完成。

#### profile 最终取 Baseline（2026-09-18）

过程：最初按「更通用的档位」把 profile 显式设为 `baseline`；随后改成 `main` 试做了一次对比准备，核对 x264 的 preset 定义后确认 Main 在当前 preset 下不带来任何收益，因此回退为 `baseline`。

理由：`ultrafast` 显式设置 `b_cabac = 0`、`b_deblocking_filter = 0`、`b_transform_8x8 = 0`、`i_subpel_refine = 0`、`i_frame_reference = 1`、`analyse.inter = 0`、`i_aq_mode = 0`。Main 相对 Baseline 多出来的能力（CABAC、8x8 变换、weighted prediction）在当前 preset 下一个都没启用，所以改 profile 只是把 `profile_idc` 从 66 改成 77：SPS 之外码流内容不变，画质不变，编码耗时也不变，但声明的兼容性比实际能力更宽。保留 `baseline` + Level 4.0 是当前配置下最保守、也最贴合实际码流的声明。

需要注意 `FF_PROFILE_H264_CONSTRAINED_BASELINE` 不能用：libx264 的 profile 映射只覆盖 `BASELINE`、`MAIN`、`HIGH`、`HIGH_10`、`HIGH_422`、`HIGH_444`，Constrained Baseline 落到 `default: break;`，profile 字符串不会被设置，写它会编译通过、运行无警告、编码器仍按自己的默认档位输出。取 `FF_PROFILE_H264_BASELINE` 后由 x264 施加 baseline 约束，配合 `max_b_frames = 0` 与 `ultrafast`，实际码流仍是 Constrained Baseline，运行日志也证实为 `profile Constrained Baseline, level 4.0`。

若将来要在同码率下提升画质，要动的是 CABAC，不是 profile 名字：libx264 没有名为 `cabac` 的 AVOption，CABAC 由 `coder` 选项控制（取值 `cavlc` / `ac`），也可以用 `x264-params` 传 `cabac=1`；写 `av_opt_set(priv_data, "cabac", "1", 0)` 会因选项不存在而失败，与 `CONSTRAINED_BASELINE` 属于同一类静默失效，落地前需核对 libx264 对 `coder` / `x264-params` 的应用顺序。届时还要同步把 profile 提到 Main 并做单变量验证，因为 `x264_param_apply_profile` 若在 `coder` 之后执行，baseline 会把 CABAC 重新关掉。

验证：最终代码与阶段 2.8 运行验证时的代码状态一致（`profile=baseline`、`level=40`、12 Mbps），Debug 构建与链接通过且仅重编 `VideoEncoder.o`，因此无需重跑即可沿用上面的运行结果与结论。

### 阶段二总体总结与结果

阶段二最终稳定配置为 1920×1080、30 FPS、GOP 30、12 Mbps、Baseline、Level 4.0 和无 B 帧。采集与编码保持 1:1，`dup = 0`、`skip = 0`；三缓冲交接等待已降至微秒级，颜色转换与软件编码合计约 9.43 ms，低于 30 FPS 的 33.3 ms 单帧预算。

### 阶段三：单独修正 PTS

目的：修正当前无符号可选 PTS 导致的时间戳语义问题，让编码帧 PTS 随采集序号递增，并在不改变帧率、码率和编码器的条件下验证结果。

实施：

- `RtmpPushManager::EncodeVideo()` 用线程局部变量记录首个 `view.sequence`，每次启动编码线程自然重新对齐；令 `framePts = view.sequence - firstSequence`，跳过采集帧时 PTS 也相应跳跃。当前编码器 `time_base = 1/30`，序号差可直接作为 PTS。
- 在 `H264Encoder.h/.cpp` 和 `VideoEncoder.h/.cpp` 中增加必传的有符号 `int64_t pts` 参数，沿调用链传递；若保留可选的 `timing` 参数，应把必传的 `pts` 放在它前面。
- `VideoEncoder` 直接设置 `out_frame->pts = pts`，删除无效的 `pts >= 0` 判断及不再使用的 `pts_` 成员。
- 暂不透传 `AVPacket::pts/dts`，不修改 `RtmpPublisher` 的 RTMP 发送时间戳，也不同时改变帧率、GOP、码率或编码器。

验证：

- 临时核对编码输入帧与输出包的 PTS/DTS：正常逐帧递增，采集序号跳跃时 PTS 对应跳跃；不只依赖编码器启动日志或拉流端警告判断。
- 推流、停止和再次推流均正常。
- 按阶段二相同方法重复测量端到端延迟，对照 9 次测量的约 59.33 ms 均值，确认没有明显退化。本阶段的编码 PTS 尚未传到 RTMP，不预期单靠此改动降低端到端延迟。

#### 代码改动（2026-09-21）

- `Pusher/RtmpPushManager.cpp:199-221`：`EncodeVideo()` 用局部变量记录本次编码线程的首个 `view.sequence`，令 `framePts = view.sequence - firstSequence`，并把 `framePts` 作为必传参数交给 `H264Encoder::Encode`。取采集序号差而不是「已编码帧计数」：编码落后跳过采集帧时序号照样跳跃，PTS 才对应画面真实发生的时刻；编码器 `time_base = 1/帧率`，序号差即帧间隔。编码线程每启动一次就重新对齐到 0，再次推流不会继承上一轮时间轴。
- `Codec/H264Encoder.{h,cpp}`：原来的隐式 PTS 换成必传的 `qint64 pts`，签名改为 `Encode(data,width,height,pts,out_frame,timing = nullptr)`，按文档要求把必传参数放在可选的 `timing` 之前，原样透传不做换算。
- `Codec/VideoEncoder.{h,cpp}`：签名同步为 `Encode(data,width,height,qint64 pts,timing = nullptr)`；`out_frame->pts = pts >= 0 ? pts : pts_++` 改为 `out_frame->pts = pts`；删除不再使用的 `pts_` 成员（含构造列表与 `Close()` 里的置零），并顺带删除只在构造函数出现过的死成员 `force_idr_`。原来的无符号 `quint64 pts = 0` 默认值使 `pts >= 0` 恒真，所以改动前每帧都被赋 PTS 0、`pts_++` 永不执行——这正是本阶段要消除的语义缺陷，也是新签名不再给默认值的原因：保留默认值等于保留「调用方漏传就静默收到 0」的入口。
- `Codec/AudioEncoder.cpp:106`：删除被下一行 `av_rescale_q` 无条件覆盖的死赋值 `in_frame->pts = pts_;`，音频 PTS 的语义与数值都不变。

预期行为不变：`ultrafast` + `zerolatency` + `max_b_frames = 0` 已关闭全部依赖 PTS 的编码器特性（prefetch、场景切换、lookahead、B 帧重排序），因此 PTS 修正不改变编码决策和码流；`AVPacket::pts/dts` 仍未透传，RTMP 时间戳继续来自 `RtmpPublisher` 自己的 `Timestamp`，所以本阶段不预期端到端延迟发生变化。

临时核对代码：`H264Encoder::Encode` 中新增 `[PTS-CHECK]` 日志，在输入 PTS 不连续或输出包 `pts/dts` 与输入不一致时打印，同时输出包的 `duration`。`lastPts` 是静态变量，因此首次推流的正常首帧（PTS 0）不打印，重新推流首帧通常会打印；正常后续帧应保持静默。`duration` 仅显示、不参与判断；验收后删除该日志。

当前状态：代码已修改（2026-09-21），Debug 构建与链接通过（仅重编 `VideoEncoder`、`H264Encoder`、`AudioEncoder`、`RtmpPushManager` 四个翻译单元），运行结果待测。

## 10. 验收标准

功能标准：

1. 推流、拉流和首次画面显示正常。
2. BGRA 画面颜色正确，没有红蓝通道颠倒。
3. 分辨率、行跨度和缓冲区大小计算正确。
4. 停止推流时采集线程与编码线程都能退出，不发生永久等待。
5. 再次建立推流时三缓冲状态能正确重新初始化。

并发标准：

1. 整帧复制和 H.264 编码期间不持有 `frameMutex_`。
2. 采集线程只写 `back`，编码线程只读 `front`。
3. 锁只保护索引、`hasNewFrame_` 和停止状态。
4. 不存在无界原始帧队列。
5. 编码落后时丢弃旧的待编码画面，而不是增加排队延迟。
6. BGRA 到 YUV420P 的转换只在编码线程执行，不阻塞采集线程。

性能标准：

1. 重复编码帧数为 0。
2. 正常逐帧路径不再动态分配 BGRA 帧缓冲区。
3. 采集完成到编码开始的等待时间相较基线明显下降。
4. 端到端延迟必须以多次样本对比，不能根据单次截图得出结论。
5. 同时记录 CPU 使用率，确认低延迟改造没有造成不可接受的持续忙等。

## 11. 风险和边界

- 三缓冲优化的是采集与编码之间的等待、复制和积压，不代表端到端延迟一定按相同比例下降。
- 本方案保留从 FFmpeg `AVFrame` 到紧凑 BGRA 缓冲区的一次复制。进一步零复制需要重新评估 FFmpeg 帧引用的生命周期，不属于第一阶段。
- 条件变量唤醒存在操作系统调度成本，但不会像固定轮询那样人为等待到下一周期。
- 三块 4K BGRA 缓冲区约占 95 MiB，必须按实际捕获分辨率计算内存成本。
- 本轮接受 BGRA 三缓冲的内存成本，以换取更小的改动范围和更轻的采集线程；YUV420P 三缓冲留到后续受控实验。
- 不建议第一版使用纯原子指针交换。固定三缓冲配合短临界区更容易证明所有权和停止流程正确。
- 本方案不处理拉流端包队列、解码帧队列或 Qt 重绘队列。完成发送端改造后，仍需用端到端时间戳判断下一处瓶颈。
